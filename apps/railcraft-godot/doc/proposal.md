## 1. 文档目的

本文档用于向后续 Coding Agent 完整传递 RailCraft Demo 的产品、内容、技术、测试和交付要求。后续 Agent 应以本文档为需求基线，在单个 Codex 可管理的复杂度内完成可运行 Demo。

## 2. 项目概述

### 2.1 项目名称

- 显示名称：**RailCraft Demo**
- GitHub 仓库名：`railcraft-demo`
- 仓库可见性：私有
- 仓库所有者：执行开发任务时，Codex 中当前已认证的用户个人 GitHub 账号
- 本地工程根目录：当前工作区的`demo/`目录
- Git仓库根目录：`demo/`目录自身；不得把游戏工程直接生成到外层现有仓库根目录

执行开发时，Agent应将本需求文档复制到`demo/doc/proposal.md`，并以副本作为新私有仓库中的需求基线。外层仓库继续保存赛项资料和前期文档，`demo/`保存完整、可独立克隆的游戏工程。

### 2.2 产品定位

RailCraft Demo 是一款 Windows 桌面端、固定3D视角、鼠标点击操作的铁路知识科普与列车装配玩法原型。

玩家通过回答铁路知识单选题获得零件。每答对一道题，玩家立即进入一次装配操作。若干小零件按固定顺序组成系统级组件，三个系统级组件最终组成一列原创通用高速动车组。

### 2.3 核心目标

首版只验证以下命题：

1. “答题获得零件—逐步装配—完成火车”的核心循环可以实现；
2. 玩家能够理解规则并顺利完成一次体验；
3. 项目结构允许后续替换为更真实的 SolidWorks/GLB 模型；
4. 单个 Coding Agent 可以维护、测试和继续扩展整个项目。

### 2.4 使用场景

- 内部玩法讨论；
- 向团队和指导教师展示初步方向；
- 讨论后续是否扩展为正式参赛作品；
- 验证题目、奖励、装配和完成反馈是否形成连贯体验。

### 2.5 内容受众

- 面向对铁路知识感兴趣的普通爱好者；
- 题目难度采用入门爱好者水平；
- 不限定具体年龄、学校、专业或课程；
- 界面和内容全部使用简体中文。

## 3. 与赛项要求的关系

项目方向需参考“工程场景数字化”赛项对真实工程对象、数字化技术、完整工程逻辑、现场体验和效果验证的要求。Demo 阶段采用较低完成度验证玩法，不宣称已经具备真实客户、真实工程部署或正式比赛成果。

当前可体现的内容：

- 工程对象：通用电力动车组的共性结构与系统；

正式参赛前仍需补充：

- 真实客户或真实教学场景调研；

- 更完整的虚实耦合或工程级原型；

## 5. 核心体验流程

```text
启动程序
→ 开始页面
→ 阅读玩法说明
→ 点击“开始体验”
→ 显示第1道题
→ 选择答案
   ├─ 错误：显示错误提示，保留原题并允许再次选择
   └─ 正确：显示正确反馈、知识解析和资料来源
→ 点击“进入装配”
→ 显示新获得的零件及发光安装位置
→ 点击零件
→ 零件播放移动与吸附动画
→ 返回下一道题
→ 每完成3个小零件，播放系统级组件完成动画
→ 完成第9个零件后，播放整车组装和完成动画
→ 显示结束页面
→ 点击“退出”关闭程序
```

整个流程没有失败结局。玩家必须通过正确回答当前题目继续前进。

## 6. 列车抽象模型

### 6.1 建模原则

- 最终列车是一列原创的通用高速电力动车组教学模型；
- 外观可吸收中国高速动车组常见的流线型车头、长条车窗及蓝红装饰语言；
- 不对应具体CRH或CR车型；
- 不使用“和谐号”“复兴号”字样、真实Logo和具体车型涂装；
- 首版使用Godot基础几何体、程序化网格或Codex能够独立生成的低多边形模型；
- 外观优先保证一眼能够辨认为高速列车；
- 专业结构采用教学抽象，避免制造具体型号均采用同一布置的误解。

### 6.2 组件和零件

| 装配序号 | 小零件 | 所属系统级组件 | 最低视觉要求 |
|---:|---|---|---|
| 1 | 车体外壳 | 车体与连接组件 | 流线型头部、长条车身、车窗区域 |
| 2 | 客室车门 | 车体与连接组件 | 可辨认的矩形车门模块 |
| 3 | 车钩缓冲装置 | 车体与连接组件 | 位于车体端部的抽象连接结构 |
| 4 | 转向架构架 | 走行与制动组件 | 位于车体下方的深色框架 |
| 5 | 轮对 | 走行与制动组件 | 由车轴和左右车轮形成的抽象轮对 |
| 6 | 制动装置 | 走行与制动组件 | 靠近车轮的制动盘或夹钳抽象件 |
| 7 | 受电弓 | 牵引供电组件 | 位于车顶、可升起的菱形或单臂结构 |
| 8 | 牵引变压变流单元 | 牵引供电组件 | 车下箱体形式的教学抽象件 |
| 9 | 牵引电机 | 牵引供电组件 | 位于转向架附近的圆柱或箱体电机 |

系统级关系：

```text
车体外壳 + 客室车门 + 车钩缓冲装置
= 车体与连接组件

转向架构架 + 轮对 + 制动装置
= 走行与制动组件

受电弓 + 牵引变压变流单元 + 牵引电机
= 牵引供电组件

三个系统级组件
= 通用高速电力动车组
```

“牵引供电组件”属于系统层面的教学归类。真实车辆中的受电弓、主变压器、牵引变流器和牵引电机通常分布在不同位置，具体布置因车型而异。游戏解析中必须说明这一点。

## 7. 初始题库

### 7.1 题库规则

- 首版使用以下9道固定顺序题目；
- 每题四个选项，只有一个正确答案；
- 每题对应一个小零件；
- 错误后只显示“回答错误，请再试一次”，不泄露答案；
- 正确后显示一句或两句解析；
- 正确反馈必须显示“来源机构、资料标题、网页地址”；
- 来源信息作为普通文字显示，运行时不要求打开网页；
- 题目、选项、答案、解析、来源和奖励零件均从数据文件加载；
- 后续可用新增数据替换题目，不应修改核心流程代码。

### 7.2 首版题目内容

#### Q1：车体外壳

题目：动车组车体的主要作用是什么？

- A. 承载乘客和车载设备，并形成车内空间
- B. 从接触网获取电能
- C. 直接驱动车轮旋转
- D. 控制铁路信号机

正确答案：A  
奖励零件：车体外壳  
解析：车体是车辆的重要承载结构，为乘客、设备和车内设施提供安装与使用空间。不同动车组的车体材料、尺寸和结构会有差异。  
来源：中国中车，《和谐号CRH6型城际动车组》  
地址：https://www.crrcgc.cc/pz/2013-12/28/article_0C37D1973CFB4C6382B32FD53F5A40B5.html

#### Q2：客室车门

题目：动车组的列车网络控制系统通常可以监视和控制下列哪类设备？

- A. 客室车门
- B. 钢轨轨距
- C. 站台长度
- D. 隧道衬砌

正确答案：A  
奖励零件：客室车门  
解析：列车网络控制系统可以对牵引、制动、供电、空调和门控等车载子系统进行监视与控制。  
来源：中国中车，《列车网络控制系统》  
地址：https://crrcgc.cc/sfs/2016-05/06/article_CB1A64A1964A46308E720DD62DE69E00.html

#### Q3：车钩缓冲装置

题目：车钩缓冲装置的主要作用是什么？

- A. 连接车辆并传递、缓和纵向作用力
- B. 调节车厢照明亮度
- C. 从接触网取得电流
- D. 测量列车运行速度

正确答案：A  
奖励零件：车钩缓冲装置  
解析：车钩用于车辆连接和牵引力、制动力传递，缓冲装置可以吸收连挂及运行中的部分纵向冲击。  
来源：中国中车，《通用机电》  
地址：https://crrcgc.cc/eportal/ui?pageId=715104

#### Q4：转向架构架

题目：位于车体下方，用于安装轮对、悬挂以及部分驱动和制动设备的结构是什么？

- A. 转向架
- B. 受电弓
- C. 客室车门
- D. 接触网支柱

正确答案：A  
奖励零件：转向架构架  
解析：转向架位于车体下方，与车体和轮对等部件形成接口，并承担走行、支承、导向和减振等任务。  
来源：国家铁路局，《城际铁路动车组铁路装备技术规范》  
地址：https://www.nra.gov.cn/jglz/sbjg/jsgf/202602/P020260227614771043169.pdf

#### Q5：轮对

题目：动车组中直接在两条钢轨上滚动的成组部件是什么？

- A. 轮对
- B. 车门
- C. 空调机组
- D. 受电弓

正确答案：A  
奖励零件：轮对  
解析：轮对由车轮、车轴等部分组成，是车辆走行系统的重要组成部分；具体结构和材料需满足相应车型与速度等级要求。  
来源：国家铁路局，《城际铁路动车组铁路装备技术规范》  
地址：https://www.nra.gov.cn/jglz/sbjg/jsgf/202602/P020260227614771043169.pdf

#### Q6：制动装置

题目：保障列车按要求减速和停车的关键系统是什么？

- A. 制动系统
- B. 旅客信息系统
- C. 空调系统
- D. 照明系统

正确答案：A  
奖励零件：制动装置  
解析：制动系统是列车安全运行的重要系统，需要按照控制指令稳定完成减速和停车。  
来源：中国中车，《CRH2型制动机》  
地址：https://crrcgc.cc/pz/2013-12/12/article_E928263DDE7244DBBF84BAE4443DAC71.html

#### Q7：受电弓

题目：电力动车组车顶受电弓的主要作用是什么？

- A. 与接触网接触并获取电能
- B. 测量车厢温度
- C. 连接相邻两节车厢
- D. 改变车轮方向

正确答案：A  
奖励零件：受电弓  
解析：电力牵引列车通过车顶受电弓与线路上方接触网保持接触，从接触网获取运行所需电能。  
来源：国家铁路局，《基于耦合动力学的高速铁路接触网/受电弓系统技术创新及应用》  
地址：https://www.nra.gov.cn/ztzl/hy/kjcx/kjxm/201802/t20180212_198465.shtml

#### Q8：牵引变压变流单元

题目：下列哪组设备属于电力列车牵引传动系统的典型组成？

- A. 主变压器、牵引变流器、牵引电机
- B. 车门、座椅、行李架
- C. 钢轨、轨枕、道砟
- D. 站台、雨棚、检票闸机

正确答案：A  
奖励零件：牵引变压变流单元  
解析：牵引设备通常包括高压电器、主变压器、牵引变流器、牵引电机及相关控制系统。Demo将变压和变流设备合并为一个抽象零件。  
来源：中国中车，《通用机电》  
地址：https://crrcgc.cc/eportal/ui?pageId=715104

#### Q9：牵引电机

题目：牵引电机在列车运行中的主要作用是什么？

- A. 将电能转化为驱动车轮所需的机械动力
- B. 为乘客提供座椅加热
- C. 控制站台广播
- D. 固定接触网支柱

正确答案：A  
奖励零件：牵引电机  
解析：牵引电机是牵引传动系统中的关键设备，通过传动装置向轮对提供驱动力。  
来源：中国中车，《通用机电》  
地址：https://crrcgc.cc/eportal/ui?pageId=715104

## 8. 交互与界面需求

### 8.1 输入方式

- 仅需鼠标操作；
- 单击按钮选择答案；
- 单击零件完成安装；
- 不实现拖放、键盘快捷玩法和手柄支持。

### 8.2 开始页面

必须包含：

- `RailCraft Demo`标题；
- 简短中文玩法说明；
- “开始体验”按钮；
- “退出”按钮。

### 8.3 答题页面

必须包含：

- 当前进度，例如“问题 3 / 9”；
- 题目文本；
- 四个清晰可点击的选项；
- 错误反馈区域；
- 正确反馈区域；
- 正确后的简短解析和来源；
- 正确后才出现的“进入装配”按钮。

### 8.4 装配页面

必须包含：

- 固定3D摄像机；
- 当前已完成的列车结构；
- 新获得的零件；
- 发光、描边或颜色变化形式的正确安装位置提示；
- 一句简短操作提示；
- 点击零件后自动移动、旋转并吸附的动画；
- 动画期间禁止重复点击；
- 装配完成后自动进入下一题或组件完成反馈。

### 8.5 结束页面

最终完成动画必须存在，包括：

- 三个系统级组件汇合或逐步显现；
- 完整列车形成；
- 车灯点亮、受电弓升起、车轮轻微转动或列车短距离驶入画面中的至少两项；
- 显示完成祝贺文字；
- 显示“退出”按钮。

最终页面的具体构图、文字和动画时长由 Coding Agent 根据复杂度决定。

## 9. 视觉要求

- 采用简洁、明亮、低多边形的科普风格；
- 在复杂度允许时提高比例、光照和材质的真实感；
- 使用基础颜色和简单材质，首版不依赖复杂纹理；
- 背景可以使用抽象车间、装配台或简洁展台；
- 车体、转向架、受电弓等关键对象需有明显颜色或轮廓区分；
- UI文本在1280×720窗口下清晰可读；
- 所有中文文字不得出现缺字、方框或乱码；
- 不使用来源不明或许可不明确的图片、字体和3D模型。

## 10. 模型替换能力

首版几何体模型与游戏逻辑必须解耦。每个零件通过唯一`part_id`和可替换场景路径引用模型。

建议数据结构包含：

```text
part_id
display_name
component_id
model_scene_path
snap_target_path
target_transform
required_previous_part_id
```

未来替换流程应满足：

1. 将SolidWorks模型转换、减面并导出为GLB；
2. 在Godot中建立新的零件场景；
3. 更新模型场景路径和安装变换；
4. 不修改答题、奖励、状态机和组件完成逻辑。

建议预留以下目录：

```text
assets/models/placeholders/
assets/models/production/
assets/models/source/
```

## 11. 数据与程序结构

### 11.1 数据驱动

题目、答案、解析、来源、奖励零件和装配配方应存放在JSON或Godot自定义Resource中。首版优先使用JSON，方便后续非程序成员修改。

必须在启动或测试阶段校验：

- 题目ID唯一；
- 每题恰好四个选项；
- 正确答案索引有效；
- 奖励零件真实存在；
- 零件ID唯一；
- 组件配方引用的零件均存在；
- 每个零件具有安装目标；
- 装配依赖没有循环；
- 9道题能够恰好完成9个零件和3个组件。

## 12. 固定技术栈

以下版本必须锁定，未经用户同意不得升级：

| 工具 | 固定版本 | 用途 |
|---|---:|---|
| Godot Standard | 4.6.3-stable | 游戏引擎与Windows导出 |
| GDScript | Godot 4.6.3内置 | 运行时代码，要求类型化 |
| 渲染器 | Compatibility | 提高Windows普通电脑兼容性 |
| GUT | 9.6.0 | GDScript自动化测试 |
| Python | 3.12.13 | 仅运行开发工具 |
| uv | 0.11.8 | Python版本与依赖管理 |
| gdtoolkit | 4.5.0 | `gdlint`与`gdformat` |
| pre-commit | 4.6.0 | 提交前检查 |

要求：

- 使用Godot Standard版，不使用.NET版；
- 不引入C#；
- 使用`.python-version`固定Python；
- 使用`pyproject.toml`和`uv.lock`固定Python开发依赖；
- GUT以固定版本提交到`addons/gut/`；
- GitHub Actions中的第三方Action必须固定到明确版本，安全允许时优先固定提交SHA；
- 在`doc/development.md`记录所有工具安装方式和版本验证命令。

## 13. 代码质量要求

- 所有GDScript使用静态类型；
- 函数参数和返回值必须声明类型；
- 开启Godot的`UNTYPED_DECLARATION`和适用的`UNSAFE_*`警告；
- 核心类型警告配置为错误；
- 代码通过`gdformat --check`；
- 代码通过`gdlint`；
- 公开类、关键状态和非直观算法需有简短文档注释；
- 禁止提交Godot缓存、导出缓存和本地凭据；
- 不提交AI生成过程文本和临时调试文件；
- 避免大规模全局单例，确需使用的管理器需记录职责。

## 14. 测试要求

### 14.1 自动化测试

至少覆盖：

1. 题库可以成功加载；
2. 题目、选项、答案和来源字段完整；
3. 错误答案不会发放零件；
4. 正确答案只发放一次对应零件；
5. 当前题目答错后仍可再次作答；
6. 零件不能违反固定顺序安装；
7. 点击正确零件后完成吸附状态；
8. 三个零件完成一个系统级组件；
9. 三个系统级组件完成整车；
10. 状态机不存在无法继续的状态；
11. 题库与零件、配方引用保持一致；
12. 主场景可以在Godot headless模式下加载，无脚本错误。

### 14.2 Windows GUI自动化验收

Coding Agent必须使用可用的Windows GUI自动操作能力运行最终Windows构建，代替用户人工验收。自动操作至少完整执行一轮游戏，并检查：

- 窗口正常启动；
- 所有中文正常显示；
- 9道题均可完成；
- 错误答案可以重试；
- 每次正确答案后只安装一个新零件；
- 发光安装位置容易理解；
- 动画期间不会重复触发；
- 最终组装动画完整播放；
- “退出”按钮可以关闭程序；
- 无明显卡顿、穿模、闪烁和控制台错误。

自动验收必须留存以下证据：

- 开始页面截图；
- 至少一次错误回答及重试截图；
- 正确回答、解析和来源截图；
- 至少一次小零件装配截图；
- 至少一次系统级组件完成截图；
- 完整列车和结束页面截图；
- 程序运行日志；
- GUT、格式检查和静态检查报告；
- 一份`artifacts/acceptance/acceptance-report.md`，逐项记录验收结果和证据路径。

截图和日志统一存放在`artifacts/acceptance/`。若执行环境缺少Windows GUI自动操作能力，Agent仍需完成可执行程序、自动化测试和日志检查，并在验收报告中明确标记“GUI验收阻塞”，不得把未执行的GUI步骤报告为通过。

## 15. 非功能要求

- 目标系统：Windows 10/11 x64；
- 运行方式：窗口模式；
- 默认窗口：1280×720；
- UI需支持窗口放大，最低适配960×540；
- 目标硬件：普通教学或办公笔记本，集成显卡可运行；

后续 Coding Agent 获得明确授权执行以下操作：

1. 使用Codex中当前已认证的用户个人GitHub账号；
2. 创建名为`railcraft-demo`的私有GitHub仓库；

GitHub操作目标必须始终为当前认证用户账号下的私有仓库`railcraft-demo`。仓库、分支、Pull Request、标签和预发布版本均已获得用户授权，无需在执行过程中再次请求确认。

GitHub工作采用以下职责划分：

首版基础几何体不依赖大型模型文件。Git LFS规则用于后续替换模型。

推荐协作规则：

- `main`始终保持可运行；
- 功能开发使用`feat/*`分支；
- 通过Pull Request合并；
- Pull Request必须通过格式、静态检查、Godot加载和GUT测试；

1. `demo/`中的完整本地工程；
2. 本地Git初始化、分支和有意义的提交历史；
3. 全部可在本地运行的格式、静态检查、GUT和Windows GUI自动化验收；
4. Windows构建压缩包；
5. 源码归档包；
6. 测试、日志、截图和验收报告；
7. `doc/handoff.md`，说明认证错误、已完成内容、未执行的远程步骤和用户恢复认证后的精确续作命令。

本地降级交付统一放在：


完成本地交付后，Agent以“本地交付完成、GitHub远程发布阻塞”的状态结束，不反复等待用户，也不声称远程仓库、Actions或Release已经完成。

## 21. 已知限制与未来方向

首版限制：

- 模型采用基础几何体或低多边形抽象；
- 题库只有9道固定题；
- 装配过程采用点击和自动吸附；
- 缺少真实用户调研、学习效果数据和工程KPI；
- 缺少实体设备和虚实耦合；
- 未针对具体动车组型号进行结构还原。

未来可讨论：

- 使用SolidWorks制作或替换真实感模型；
- 扩充随机题库和知识树；
- 增加和谐号风格、复兴号风格等原创皮肤；
- 增加部件拆解观察和自由旋转；
- 增加多人协作和资源机制；
- 增加铁路线路、接触网、信号和调度知识；
- 开展用户调研并定义学习效果KPI；
- 加入实体沙盘或传感器，形成虚实耦合体验；
- 按赛项评分标准完善真实问题、技术作用、验证数据和现场体验。
