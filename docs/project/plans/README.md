# 项目计划登记规则

本目录保存当前 Unity 第三人称白盒及其后续正式化工作的项目计划。Godot 启动期的
`proposal.md`、`detailed-design.md`、`prompt.md` 和 `tasks/` 已冻结在上级目录，
继续作为历史项目基线，不迁移为当前计划。

## 计划状态

每份计划使用 `YYYY-MM-DD-topic.md` 命名，并在开头记录：

- 状态：草案、进行中、已完成或已取代；
- 目标与明确排除项；
- 负责人或执行批次；
- 依赖的需求、交付资料和 ADR；
- 验收命令与证据目标路径。

计划完成后保留原内容和完成日期。后续方向变化时新增计划，并将旧计划标为“已取代”
及链接替代计划；避免重写历史步骤，让当时的范围与证据可以复核。

## 当前计划边界

- 当前开发主线：`apps/railcraft-unity/Assets/RailCraft/ThirdPerson/`
- 当前范围：58题、14零件、6装配节点、调试闭环和 Blender 视觉替换
- 当前规格：`apps/railcraft-unity/Documentation/ThirdPersonWhitebox.md`
- 当前证据：`apps/railcraft-unity/Artifacts/Whitebox/Acceptance/`
- 冻结 Unity v0.1 与 Godot Demo 的功能扩展不进入本目录的活动计划

`.superpowers/` 和 `docs/superpowers/` 中的工具执行稿不会自动成为项目计划。需要
长期保留时，应先核对实际完成状态、去除临时命令和本机路径，再以明确状态迁入本目录。

## 批次提交与推送

1. 把计划拆成可单独验证的批次，例如领域逻辑、玩家交互、流程场景、题库、美术替换
   或验收证据；一个批次只承担一个主要目标。
2. 每批同步实现、测试、必要文档和最终证据。运行相应测试、Windows 构建和成品冒烟，
   在计划中记录实际结果。
3. 通过验证后创建独立提交；提交前检查 `git diff` 与 `git status --short`，排除缓存、
   Build、临时文件、原始交付和其他批次改动。
4. 每个完成批次及时推送当前功能分支，使远端持续具备可审查的恢复点。共享分支不做
   强制推送，不把多个无关批次积压到一次最终提交。
5. 验收证据与产生它的实现同批提交；若证据需要在另一台机器补采，使用紧随其后的
   独立证据提交，并在计划中关联实现提交。
